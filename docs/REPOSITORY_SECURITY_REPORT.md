# Repository Security Report — Production Artifact Cleanup

**Date:** 2026-07-14
**Scope:** Full repository security audit and cleanup of `emanoelatef2026/robocode-website` (public GitHub repository). Triggered after a routine QA-script push was blocked for embedding production UUIDs, prompting a complete sweep rather than a one-off fix.
**Type of change:** Repository hygiene only. No application behavior, business logic, database schema, or migration was modified.

---

## 1. Executive Summary

The repository contained three genuinely sensitive, production-derived artifacts that should never have been committed, plus real production UUIDs scattered across three historical diagnostic/prompt documents. All of it has now been removed from `HEAD` and, where the document was still useful as a reference, sanitized with placeholders instead of deleted outright.

**The single most important finding:** `.claude/settings.local.json` — a local AI-assistant tool-permission cache, not application code — has been tracked in git since the repository's very first commit and contained a credential-shaped value for the `x-bootstrap-secret` header that matches the exact contract still used by the live `app/api/bootstrap/route.ts` endpoint today (see `app/api/bootstrap/route.ts:3,16-17` for the contract; the literal value itself is deliberately **not** reproduced in this report — see §8). **This should be treated as a live credential exposure regardless of any git-history decision.**

Second most important: `backfill-org-emails-1783338736875.csv`, a full dry-run export from a real production email-migration script, containing 137 rows of real user UUID + real personal email (old and new) + role. This is a straightforward PII leak.

Everything classified **Critical** or **High** below has been removed from `HEAD` in this cleanup commit. Nothing in `app/`, `modules/`, `components/`, `supabase/migrations/`, or any other application/schema path was touched — only repository-level artifacts (a data export, a local tool-settings file, a CLI cache directory, `.gitignore`, and prose in `docs/`).

## 5. Secret Scan Results (Task 5)

Pattern-based scan across every tracked file for: `@gmail.com`, `@robocodeschools.com`, UUIDs, `service_role`, `anon`, `Authorization`, `Bearer`, `OPENAI`, `SUPABASE`, `RESEND`, `TOKEN`, `PASSWORD`, `SECRET`, `BEGIN PRIVATE KEY`, `PRIVATE KEY`, `ACCESS KEY`, `DATABASE_URL`, plus common live-key shapes (`sk_live_`, `sk-`, `re_`, `whsec_`, `AIza`, JWT `eyJ...` triples).

**Result: zero literal secrets found in the current tree** (`HEAD` after cleanup). All matches were one of:
- Env-var reads (`process.env.X`) — correct usage, no literal value in source.
- Role/permission *names* in RLS SQL (`service_role`, `anon`) — expected, not credentials.
- Test/seed fixture passwords (`Test@12345`, `Parent123`, `Ali123` in `scripts/seed/generate-test-data.ts` and `tests/welcome-message/*.test.ts`) — synthetic, local-only, not real credentials.
- False-positive substring matches (e.g. `pre_enrollment` matching a `re_[A-Za-z0-9]{10,}` Resend-key-shaped regex).
- The two real findings already covered in §2 (the legacy admin password and the bootstrap-secret value, both inside the now-removed `.claude/settings.local.json`).

One item flagged but **intentionally not changed** (would require modifying application behavior, which was explicitly out of scope):

- **`app/api/book-session/route.ts:58`** — the trial-booking notification email's `to:` recipient is hardcoded to a real personal Gmail address (not reproduced in this report — see the file directly) rather than sourced from an environment variable. This is a real personal email in public source, but it is live, intentional business logic (where booking notifications currently get delivered) — removing or changing it would alter application behavior, which this cleanup was explicitly told not to do. **Recommendation (not applied): move this to a `BOOKING_NOTIFICATION_EMAIL` env var**, the same pattern already used for `INTEGRITY_ALERT_EMAIL` in `.env.example`. Classified **Medium** — real PII, but low exploitability (it's a mailto recipient, not a credential) and clearly intentional.

Also reviewed and explicitly **not flagged for action**: the Supabase project ref `fkqwafedruparlqjiprq` appears in 9 tracked files (docs + this report). It is **not a secret** — it is the same value shipped client-side in production via `NEXT_PUBLIC_SUPABASE_URL` (`https://fkqwafedruparlqjiprq.supabase.co`), so it is already public by design, protected by RLS and key-based auth rather than obscurity. Treating it as sensitive would be performative and was skipped.

**No git history rewrite was performed in this session** — per your explicit instructions, that action requires your separate authorization and was intentionally left as a documented recommendation, not executed.

**What a rewrite would involve, if you choose to proceed later:** `git filter-repo` (recommended over the deprecated `git filter-branch` or BFG for a repo this size) to strip `backfill-org-emails-1783338736875.csv` and every historical revision of `.claude/settings.local.json` from all 209 commits, followed by a coordinated **force-push** to `origin/main` and a **mandatory secret rotation** (see §8) — anyone who already cloned or forked the repo before the rewrite retains the old history locally, so a rewrite reduces future exposure but does not retroactively un-expose data that may have already been seen or scraped. This is a disruptive, one-way operation (invalidates all existing clones/forks/PRs against the current history) and should be scheduled deliberately, not run reactively.
